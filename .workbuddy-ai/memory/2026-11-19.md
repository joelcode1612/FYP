## Property Owner mobile navigation transitions (branch joel, uncommitted)

Root causes found and fixed in `fyp_mobile_app`:
- `ProviderTabHost` used an eager `IndexedStack`: Profile's three API calls and
  the Add wizard were built while Home was loading. It also pushed Add as a
  fresh `MaterialPageRoute` through `AuthGuard` on every dock tap, with no
  duplicate-tap guard, and re-keyed/refetched all tabs after any Add return.
- `MobileAppShell.go` always used `pushReplacementNamed`, so Add's own dock
  replaced the form with a new workspace shell and lost unfinished input.

Implemented:
- Add Property is now the fifth persistent `IndexedStack` page in the same
  shell, built lazily on first use and kept alive. Host chrome is hidden while
  it is selected so the form's own single top bar/dock remains unchanged.
- New `ProviderTabScope` is a command-only bridge; dock taps and Home/Profile/
  Listings shortcuts select existing tabs, never push duplicate shells.
- Draft resumes from Home/Listings remain drill-ins, with a single in-flight
  guard and tab-result commands for returning to the previous tab.
- Listing mutations refresh Dashboard/Listings only via `ServiceLocator.listingsRevision`;
  plain back-navigation no longer refetches or re-keys pages.
- Android Back from Add returns to the tab that opened it; other tabs keep the
  existing return-to-Home rule.

Files: `provider/shell/provider_tab_host.dart`, new `provider_tab_scope.dart`,
`shell/mobile_app_shell.dart`, `shell/mobile_navigation.dart`,
`entrepreneur/pages/sitewise_add_property_mobile_page.dart`,
`provider/pages/provider_dashboard_mobile_page.dart`,
`provider/pages/provider_listings_mobile_page.dart`,
`provider/pages/provider_profile_mobile_page.dart`,
`test/provider_routing_test.dart`, `test/provider_refresh_test.dart`.

Verify: `flutter analyze` clean; full mobile suite 82/82 passed.
No backend/auth/route-table/UI-theme changes; no commit or push performed.

## Entrepreneur web Recommendations dropdown labels (branch joel, uncommitted)

`fyp_jaspr_web/lib/pages/entrepreneur/recommendations_page.dart`:
- `_optionPairs` (State, City / District, Property type) now renders only
  `FacetOption.label` (falling back to `value`), e.g. `Selangor`, not
  `Selangor (117)`.
- `_rangePairs` (Property size and advanced range facets) renders only
  `FacetRangeOption.label`.
- `_advancedControl` value options (Target Market and other advanced facets)
  use the same label helper.
- Monthly rental options and the custom/unavailable selected options render
  only the interval name; the existing facet status/note still explains zero
  matches or a saved custom range.

Option `value`s, `total`s, leave-one-out facet requests, dependent dropdown
refresh, filtering and ranking were untouched. No mobile/backend/model files
changed; no duplicate component created.

## Entrepreneur mobile Recommendations filters (branch joel, uncommitted)

Fixed the existing mobile filter sheet in
`fyp_mobile_app/lib/presentation/mobile/entrepreneur/pages/entrepreneur_recommendations_mobile_page.dart`:
- All dropdowns now use `isExpanded`, bounded `menuMaxHeight`, ellipsised item
  labels and no per-option counts. Backend option labels/ranges are used, so
  `Selangor (117)` and raw `900.0|1800.0 (unavailable)` no longer appear.
- Rental and size fields use the backend interval label; a saved/custom
  non-generated interval stays selected and is explained by a clearable note.
- Target market now supports the shared `layoutPreferences` list with compact
  selected/unselected chips and a `N target markets selected` summary.
- Facet refresh now reports loading/errors with Retry instead of silently
  keeping stale choices. Zero-match state shows backend `matching_total == 0`
  plus `relaxations` clearing actions and Clear all.
- Bottom sheet uses safe area + view insets; Clear all / Show properties are
  in one non-overlapping action row. Uncommitted drafts survive dismiss via
  `_filterDraft`; applying or clearing clears it.

Root parity facts: both apps use shared `RecommendationSearchRequest` and
`ApiRecommendationSearchRepository`; filter options come from
`GET /api/v1/recommendations/facets`, results from
`POST /api/v1/recommendations/search`. State dropdown differences are
contextual leave-one-out facets: different applied constraints legitimately
produce different option/count sets; no mobile slicing or fabricated options.

Verify: `dart analyze` has only pre-existing infos in preferences page; full
mobile suite 82/82 passed. No backend/shared/model changes; no commit/push.
