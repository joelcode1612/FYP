# 2026-11-18

## Admin User Management made read-only for roles (branch joel, uncommitted)

Goal: admins can VIEW roles but never change them; roles come only from
registration / invitation / onboarding provisioning.

Backend (`backend/src/sitewise/api/v1/users.py` — `admin_update_user`):
- `PATCH /api/v1/users/{id}` now REFUSES any payload containing `role` with
  422 structured detail `{code: "role_change_not_supported", message}` BEFORE
  any identity/local write and without an audit event (fail closed, whole
  payload refused — no partial application). This was the ONLY unrestricted
  role-change write in the API; `staff.py` update_user calls are status-only
  (onboarding activation), so provisioning paths are untouched.
- Account-status + profile writes on the same endpoint preserved (identity →
  mirror → audit order unchanged; audit action now always `status.changed`).

Frontend (`fyp_jaspr_web/lib/pages/admin/`):
- `user_detail_page.dart`: Role dropdown removed; role renders as read-only
  text + policy note ("assigned by the authorised registration, invitation
  and onboarding workflows"); Save sends ONLY `account_status`; role-echo
  confirmation and `_canonicalRole` deleted; `_roleValue` fixed so
  `AppRole.owner` maps to `'owner'` (Property Owner was being labelled/
  filtered as Entrepreneur).
- `users_page.dart`: already role-read-only (badge per row); FIXED a real
  latent bug — `_selectField` used `events<String>` but Jaspr delivers select
  onInput as `List<String>`, so the Status AND Role filters NEVER fired.
  Now `events<List<String>>(onInput: (s) => onChanged(s.first))` — same
  working pattern as the detail page's status dropdown.
- New probe `tool/probe_admin_users_readonly.js` (playwright + session
  harness + stubbed `/api/v1/users*`): 20/20 checks — role badges, no role
  select in table/detail, Role+Status filters actually narrow rows, detail
  Save PATCHes `account_status` only (never `role`).
