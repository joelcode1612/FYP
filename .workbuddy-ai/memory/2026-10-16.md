# 2026-10-16 (later) — ROOT CAUSE of the recurring port clash; `serve.ps1` added

The 8090/EADDRINUSE failure hit a **4th time**. This time the cause was proven
rather than assumed.

## Proven root cause: Windows does not kill children when a console closes
Process tree of the stale server:

```
PID 14852  <terminal>              <- GONE (user closed the window)
  └─ 16552  dart.exe   (jaspr CLI)      <- ALIVE
       └─ 27832  dartvm.exe      :8090   <- ALIVE  (uptime 3h 23m)
            └─ 29004  dartaotruntime  :8181 <- ALIVE
```

The **grandparent terminal was dead** but the whole `jaspr serve` chain below it
was still running after **3 h 23 min**. On POSIX, closing a terminal sends
`SIGHUP` to the process group and the children die. **On Windows they do not** —
`dart.exe` is not in a job object, so closing the console orphans the tree.

So the mechanism is: start `jaspr serve` → close the terminal → the server keeps
serving (holding 8090) → every later `jaspr serve` fails to bind while the OLD
server serves OLD assets. Indistinguishable from "my code changes did nothing".

## Fix: `fyp_jaspr_web/serve.ps1`
Launcher that clears the port before starting.
- Reads the port from **`pubspec.yaml`** (`jaspr.port`), the same source jaspr
  uses, so the two cannot drift
- Finds the listener via `Get-NetTCPConnection`, then walks the **Dart-only**
  parent chain and kills child-first
- **Refuses to kill a non-Dart process** — reports it and exits 1 instead, so an
  unrelated service on the same port is never harmed
- `-CheckOnly` (detect + clean, do not start), `-NoKill` (report only),
  `-Port <n>` (override)

Usage: `powershell -ExecutionPolicy Bypass -File .\serve.ps1`

## BUG FOUND BY TESTING — `Process.Parent` does not exist on PowerShell 5.1
First implementation walked the chain with `$cursor.Parent`. It returned a
**depth-1 chain** — it never ascended, despite the parent being `dart.exe`.

Root cause: **`System.Diagnostics.Process.Parent` is a .NET Core addition. On
Windows PowerShell 5.1 it is `$null`**, so `while ($cursor.Parent -and …)` never
entered the loop. The script would have killed only the port holder and left the
CLI alive — the exact failure it existed to prevent.

Fixed with `Get-CimInstance Win32_Process` → `ParentProcessId`, which works on
both 5.1 and 7+. Verified: `dartvm#24840 <- dart#21756`, depth 2, halting
correctly at `cmd.exe`.

**Lesson: never use `Process.Parent` in PowerShell meant for 5.1. Use CIM.**

## Sandbox constraints to remember
- **PowerShell cannot be invoked from Bash** — use the PowerShell tool.
- **`Start-Process` is blocked** for detached processes.
- **`Invoke-Expression` is blocked.**
- `sc.exe` and `wmic` are blocked.
- For long-running servers use Bash `run_in_background`, not PowerShell.
