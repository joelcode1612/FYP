## Design decisions worth remembering
- **Every** variable is reported, including `NO_BENCHMARK` / `INSUFFICIENT_DATA`.
  Filtering to evaluated rows only would let coverage look better than the
  evidence supports.
- Healthy variables emit **no** recommendation. Filler "keep doing what you're
  doing" rows would pad the list and inflate apparent thoroughness.
- Explanations are **deterministically template-composed** (`getExplanation`), not
  Gemini-generated — no API key is configured. This still satisfies FR-32 and
  makes FR-33/FR-34 impossible to violate.
- The mobile questionnaire shows the adaptation trace inline; hiding it would
  leave the respondent unable to judge the adaptive selection.

# 2026-10-09 (later) — AI-DSS crash fixed + UI design review

## P0 bug found and fixed: `BoxConstraints forces an infinite width.`
**Root cause.** `SitewiseCtaButton` is `SizedBox(width: double.infinity)`. A `Row`
hands its non-flexible children **unbounded width**, so an infinite width trips a
hard assertion at `rendering/box.dart:611` and renders the red error screen. This
is why the user "clicked the assessment tab and could not see the web page".

Six sites placed it in a `Row`: `create_assessment_web_page.dart:149`,
`assessment_overview_web_page.dart:395` and `:566`, `assessment_findings_web_page.dart:66`
(via `WebTopBar.actions`, whose row is `web_topbar.dart:36`) and `:681`,
`assessment_recommendations_web_page.dart:493`.

**Fix.** Added an optional `width` to `SitewiseCtaButton` (default stays
`double.infinity`, so every `Column` usage is untouched) and passed finite widths
in the six Rows. Chosen over wrapping each call site in a `SizedBox` because it
documents the constraint and prevents recurrence.

**Lesson worth keeping:** a full-width widget (`width: double.infinity`) must never
go directly into a `Row`/`Column` main axis. Static analysis does **not** catch
this — it is a runtime layout assertion, so only running the app finds it.

## P0 bug: mobile assessment flow was a dead end
`startAssessment()` had exactly one caller — the **web** create page. On the mobile
tree `/entrepreneur/assessment/create` mapped to the question page, so the session
was always null and it showed "No question is available."
Added `lib/presentation/mobile/entrepreneur/pages/create_assessment_mobile_page.dart`
and routed the mobile branch to it. Also made `_falling()` branch on whether a
session exists: no session → "Start assessment" (to create), session → "View
progress" (to complete). Previously both cases offered "View progress", which was a
dead end when there was nothing to view.

## Design-token cleanup

`Color(0x...)` literals in `lib/presentation` — and the same four wash colours were
duplicated across **seven** files. Added `successWash` / `warningWash` /
`dangerWash` / `neutralWash` to `SitewiseColors` and replaced all 17 usages
