## Admin Location Intelligence backend integration

Root cause of "0/64, no valid coordinates, every action disabled": the queue
refuses to measure an unknown point, and nothing ever turned a saved address
into coordinates unless the client happened to send an
`address_confirmation_token`. The only verification row (`property_id` 11906)
had `address='dhdhdhd'`, no lat/lon, no verdict.

New `backend/src/sitewise/services/property_location_service.py`:
- `resolve_property_coordinates(session, property_id, queue_measurements=)` —
  reuses `address_preview_service.preview_address` (Google AV → Nominatim) and
  `FypPropertyRepository.set_address_validation`, then `enqueue`. Never
  re-geocodes a located listing, never invents a point.
- `address_is_geocodable()` — cheap read used by the admin GET payload.

Geocoder fix (`address_preview_service.py`) — the real reason nothing resolved:
- Nominatim returns nothing when the query contains `W.P. Kuala Lumpur`; added
  `_QUERY_STATE_ALIASES` (`W.P. X` → `X`). KL/Putrajaya/Labuan addresses now
  resolve (verified: `Jalan Ampang 1` → 3.1577542, 101.7131662).
- `_osm_query_variants()` — full → drop postcode → drop state, always keeping
  the street line (a street-less query would return a district centroid).
- `_osm_result_names_street()` — every distinctive street token must appear in
  the result. Nominatim fuzzed `Jalan SS2/24` into `Jalan SS2/72`; that match is
  now rejected as `not_found` instead of storing a wrong location.

Endpoints (`api/v1/property_verification.py`):
- GET `location-intelligence` adds `address_resolution {geocodable, missing_fields}`.
- `analyze` and `recalculate`/`retry/{category}` resolve coordinates first
  (`queue_measurements=False`; the endpoint decides what to queue) and return
  `location`; the provider reason replaces `reason` when nothing was queued.
- `submit_for_verification` geocodes before the address gate and accepts
  `VERIFIED_ADDRESS_STATUSES` instead of only `validated` (Nominatim can never
  return `validated`, which made submission impossible without a Google key).

Automatic pipeline: `_resolve_location_after_save()` in `api/v1/properties.py`
runs after the create/patch commit (own transaction — geocoding is HTTP and must
not hold the row lock), then `enqueue` + the existing `expanded64-enrichment`
worker produce measurements, the `Expanded64_v2` score and SHAP.

Frontend: `LocationResearchAssociation.addressGeocodable/addressMissingFields`
(`_wireMap`/`_wireStringList` helpers); `_canAnalyse()` replaces every
`!hasCoordinates` disable; `_pipelineLabel()` derives the status from persisted
state; `_selectTab()` fetches the live payload on tab open (the embedded
association is stale and lacks `address_resolution`);
`queueLocationIntelligence` now returns the backend's reason instead of a
hardcoded success message.

Verified: property 939 reads 63/64 calculated, score 0.473, model
`Expanded64_v2`, explanation present. 916/916 catalogue properties measured and
predicted; queue 7283 current / 45 unavailable / 0 pending.
