# 2026-10-10 (later) — Jaspr feasibility analysis (no code changed)

User asked: "can you modify the flutter web code by using the Jaspr".

## What Jaspr actually is
Jaspr (`schultek/jaspr`, v0.23.x as of Sep 2026) is an **alternative to Flutter
Web**, not a plugin or a drop-in. Its own README: *"Jaspr was made with the premise
to make a web-framework that looks and feels just like Flutter, but renders normal
HTML and CSS."* The Flutter team's own line, which Jaspr quotes: *"Flutter Web is
for building Web-Apps, not Web-Sites."*

Consequences that decide the question:
- It is a **separate project** with its own CLI (`jaspr create/serve/build`). It
  cannot live inside a Flutter app's `lib/` — `flutter build web` will not compile it.
- Components are HTML/CSS (`div`, `span`, `text(...)`), **not Flutter widgets**.
  Nothing is reusable — every screen is a rewrite, not a "modification".
- `jaspr_flutter_embed` goes the *other* way (embedding Flutter into Jaspr).

## Measured scope in this repo
- Whole web tree: **33 files, 6,188 lines** (`lib/presentation/web/`)
  - admin 8 files, entrepreneur 10, property_owner 7, landing 2, shell 4, widgets 2
- Landing page alone: **1,705 lines** (`landing_web_page.dart` 321 +
  `landing_web_sections.dart` 1,384)
- Web shell (sidebar/topbar/nav/shell): **866 lines**
- Web-only widgets: **377 lines**
- Plus **20** `lib/presentation/shared/widgets/*` that the web tree consumes

## Blockers / conflicts worth remembering
1. **ASR-1 conflict.** The project report requires "Flutter Mobile + Web, one
   codebase". Moving web to Jaspr makes it **two codebases** — this changes the
   report's architecture claim, not just the code.
2. **State layer is Flutter-coupled.** `AppState` and the role viewmodels extend
   `ChangeNotifier` (`package:flutter/foundation.dart`). A Jaspr app cannot use
   that; it needs a pure-Dart notifier/stream/signals replacement.
3. **Even the "pure data" file is coupled.** `lib/presentation/shared/landing/landing_content.dart`
   is content-only but imports `package:flutter/material.dart` because it stores
   `IconData`/`Icons`. Reuse would need the icons mapped to strings/classes first.
4. **No verification possible here.** `jaspr serve`/`jaspr build` cannot run (the
   Windows pipe-pool problem blocks Dart subprocess spawning), so any Jaspr output
   could only be `dart format`-checked and reviewed, never rendered.

## The genuine motivation for Jaspr
**SEO.** Flutter Web paints to a canvas, so crawlers see essentially nothing. The
landing page is the only public, pre-auth, SEO-critical surface — everything else
is behind login, where SEO is irrelevant. Hence "landing page only" is the
defensible scope; the full-app rewrite buys little and costs a second codebase.

## CORRECTION — the verification above had a gap (same day)

The user's IDE reported two real errors that my "zero errors" claim had missed:

```
error: The name 'runApp' is defined in the libraries
  'package:jaspr/src/server/run_app.dart (via package:jaspr/server.dart)' and
  'package:jaspr/src/stub/run_app_stub.dart (via package:jaspr/jaspr.dart)'.
  (ambiguous_import at lib\main.dart:17)
error: 'Document' isn't a function. (invocation_of_non_function at lib\main.dart:18)
error: The name 'Document' is defined in the libraries
  'package:jaspr/src/components/document/document_client.dart (via jaspr.dart)'
  and '.../document_server.dart (via server.dart)'. (ambiguous_import)
```

### Root cause
`lib/main.dart` imported **both** `jaspr/jaspr.dart` and `jaspr/server.dart`.
Each exports its own `runApp` and `Document` (client stub vs server impl), so
every use of either name became ambiguous. `Document` then "isn't a function"
because resolution failed.

**The import rule (important for every future file):**
| File kind | Import |
|---|---|
| Entry point — uses `runApp`/`Document` | `jaspr/dom.dart` + **`jaspr/server.dart`** |
| Components/pages — use `div`/`text`/`StatelessComponent` | `jaspr/dom.dart` + **`jaspr/jaspr.dart`** |

`jaspr/dom.dart` is safe in both. Only the `runApp`/`Document` pair collides.
This matches the official example, which imports exactly `dom.dart` + `server.dart`.

### Why I missed it — the real lesson
`tool/typecheck.dart` did **not** import `lib/main.dart` (I wrongly assumed
`main.dart` could not be compiled to JS because `server.dart` might pull in
`dart:io`). So the harness never checked the entry point, and reported a clean
run while `main.dart` had two errors.

**`dart compile js lib/main.dart` is the primary check** — it compiles the real
entry point and everything reachable from it. It works fine and produced
1,405,690 characters of JS. The harness is only a supplement for components the
app does not currently reach. Both are now run; both are clean.

Generalised lesson: **a verification harness must cover the real entry point.**
A green harness that excludes part of the app is worse than no harness, because
it manufactures confidence.

### Also learned
- `dart compile kernel` **spawns `gen_kernel_aot` as a subprocess** → hits the
  pipe-pool wall. Only `dart compile js` runs the front end in-process, so it is
  the only compiler-based check available on this machine.
- The **IDE analyzer works** even though the CLI does not. The user's Android
  Studio reported these errors precisely. Worth asking them for IDE diagnostics
  rather than relying solely on `dart compile js`.
