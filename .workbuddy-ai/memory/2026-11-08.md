## Android `ProtocolMessageEnum` build failure (2026-11-08, afternoon)

- SYMPTOM: `flutter run` -> `assembleDebug` -> "Failed to apply plugin
  com.android.internal.application / Could not generate a decorated class for
  type AppPlugin / com/google/protobuf/ProtocolMessageEnum". NOT a dependency
  version problem and NOT a Dart/Gradle source error (AGP 9.0.1 + Gradle 9.1.0
  + Kotlin 2.3.20 + JDK 17/JBR 21 are all a valid combination).
- REAL ROOT CAUSE (from ~/.gradle/daemon/9.1.0/daemon-34220.out.log, DEBUG):
  `Caused by: java.util.zip.ZipException: Invalid CEN header (invalid extra
  data field size for tag: 0x442f at 65512)` while Gradle 9.1's instrumentation
  agent tried to instrument
  `com/google/wireless/android/sdk/stats/GradleBuildProject$PluginType`.
  That "pending instrumentation exception" then blocked loading
  `com.google.protobuf.ProtocolMessageEnum` in the same classloader scope, so
  the visible error is a red herring. The bad jar state was latched in the
  long-lived daemon (PID 34220, Android Studio JBR 21), which the IDE kept
  reusing — every build failed in 2-8s.
- DIAGNOSIS METHOD that settled it: `gradlew help --stacktrace --no-daemon
  --offline` (fresh JVM) -> BUILD SUCCESSFUL; forcing JAVA_HOME to the JBR 21
  but reusing the daemon -> FAILED; JBR 21 + `--no-daemon` -> SUCCESS.
  A 1761-jar Python zipfile scan + strict CEN extra-field scan of 551
  instrumented jars found no on-disk corruption, so the latch was daemon-local.
- FIX (no project files changed): `cd fyp_mobile_app/android && gradlew.bat
  --stop`, then rebuild from the IDE so a fresh daemon starts. Post-fix daemons
  (23644, 35112) show ZERO ProtocolMessageEnum occurrences; `assembleDebug`
  then configured cleanly with JBR 21 and advanced into the dartcv4/OpenCV
  native-assets hook (long C++ rebuild) instead of failing at configuration.
- IF IT RECURS: clear the regenerable cache `%USERPROFILE%\.gradle\caches\
  9.1.0\transforms` (ask before deleting) and re-run. Optionally pin
  `org.gradle.java.home` to JDK 17 in android/gradle.properties, but that
  hardcodes a machine path and does NOT address the corrupt-jar latch.
- UNVERIFIED: a full fresh APK was not produced this session — the long native
  OpenCV build was still BUSY and was stopped to leave a clean daemon for the
  IDE. Existing app-debug.apk is from 03:31 today.
