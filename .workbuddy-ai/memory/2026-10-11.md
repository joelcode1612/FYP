## Correction to the brief's premise: there are NO BLoCs

The brief repeatedly asks to migrate BLoCs. There are none:
`grep -rl "package:bloc|flutter_bloc|riverpod|provider|get_it" lib/` → no matches.
Actual state layer:
- 7 × `ChangeNotifier` (`AppState`, `OnboardingController`, 5 viewmodels)
- 1 hand-rolled static-field `ServiceLocator` (global mutable state — the brief's
  §8 explicitly warns against this)

So the migration is **`ChangeNotifier` → `Cubit`**, a rewrite not a relocation.
Every `ChangeNotifier` imports `package:flutter/foundation.dart`, which is why
none of them can live in a framework-free package.

User asked what percentage of their 360° capture brief is complete.

## Verdict
**≈65% overall**, but the right 65%: core capture workflow ≈85%, cloud/production

## What IS implemented (genuinely, verified by reading)
- **26-point rig — complete.** `shared_logic/.../capture_target_data_source.dart`.
  Exactly 8 upper (pitch +45) + 8 middle (0) + 8 lower (−45) + ZENITH + NADIR.
  Each point has per-axis tolerances, previous/next frame links, expected deltas,
  and `overlapNeighbors` stitching metadata.
- **Capture FSM — complete, better than the prototype.**
  `fyp_mobile_app/lib/application/services/panorama_capture_service.dart` (306 lines),
  10 states. Enforces: 5-poll tracking warm-up, origin drift >0.5 m blocks alignment,
  800 ms stability gate, **never advances without a confirmed image**, duplicate
  rejection, retake via `reopenFrame`, resume via `restoreFrames`/`prepareResume`.
- **Quaternion alignment maths — complete and gimbal-lock safe.**
  `lib/core/utils/ar_math.dart` uses `cameraRotation.conjugated().rotated(...)`
  rather than Euler angles, so zenith/nadir don't gimbal-lock. Handles 355°→0° wrap.
- **Real ARCore capture** via `ar_flutter_plugin`: `getCameraPose()`, `snapshot()`
  → PNG. Replaces the prototype's `onpointermove` drag simulation.
- **Real persistence**: `CaptureFrameStore` → `<appDocs>/sitewise/tours/<id>/frames/`.
- **Real stitching**: `opencv_dart` `cv.Stitcher.create(PANORAMA)` + `stitchAsync`.
- **17 tests** in `test/panorama_capture_test.dart` covering the rig, wrap, FSM,
  duplicates, retake, drift, resume, generation validation.

## Critical gaps (priority order)
1. **No AE/AWB lock — highest risk.** `grep -rniE "exposure|whitebalance|awb|focuslock"`
   → zero matches. ARCore exposes no exposure API, so the camera stack must change
   to `camerawesome` (Camera2 `CONTROL_AE_LOCK`). The brief says without this the
   exposure difference between a dark corner and a bright window makes stitching
   impossible — so the stitcher will fail on real rooms despite everything else
   being correct.
2. **Stitching is ON-DEVICE**, but the brief warns of OOM for 26 hi-res frames.
   Needs the backend (Supabase + Render FastAPI) or downscaling.
3. **No blur detection** (subsystem E absent). `opencv_dart` is already a dep, so a
   Laplacian-variance check is cheap. Currently a blurry frame poisons the whole
   panorama and is only discovered after all 26 captures.
4. **No multi-station** (the prototype's Small/Medium/Large logic did not survive).
5. **No hotspots** — `grep -rni "hotspot"` → zero. Multi-station tours couldn't be
   navigated even if stations existed.
6. **Stability is time-based (800 ms hold), not gyro angular-velocity delta (1.3 s).**
   Works, but can't distinguish "holding still" from "moving slowly on target".

## Dependency reality
Present: `opencv_dart`, `panorama`, `ar_flutter_plugin`, `vector_math`.
**Absent: `camerawesome`, `camera`, `motion_sensors`, `sensors_plus`,
`supabase_flutter`, `webview_flutter`.**
