# 2026-10-14 (later still) — ROOT CAUSE of "UI not changed": a stale dev server

The user ran `dart run jaspr_cli:jaspr serve` and it **built successfully** but
failed to bind:

```
SocketException: ... errno = 10048, address = 0.0.0.0, port = 8090
```

`10048` is `EADDRINUSE`. `netstat -ano` showed **PID 28716 (`dartvm.exe`)
LISTENING on 0.0.0.0:8090**, with an established link to the VM service on 8181
(PID 33604, its child).

### Why this explains everything
An **older `jaspr serve` instance was still running and holding port 8090**. So:
- Every restart the user attempted **failed to bind**
- The old instance kept serving the **old built assets**
- The browser therefore showed the old UI, making it look like my icon / CSS
  changes had never been applied

Combined with the duplicate `.map-pin` block found in the same session, there
were **two independent reasons** the UI appeared unchanged, neither of which was
"the code is wrong".

### Fixed
`taskkill /PID 28716 /F` → *"SUCCESS: The process with PID 28716 has been
terminated."* PID 33604 had already exited with its parent. Ports 8090 and 8181
are now free (only `TIME_WAIT` entries remain, which clear themselves).

### Lesson to apply first, next time
**Before concluding a web change didn't take effect, check for a stale server
holding the port.** `netstat -ano | grep :8090` and look for a LISTENING pid. A
dev server that failed to rebind keeps serving stale assets and gives the exact
symptom of "my edits did nothing".

Also worth noting: `dart run jaspr_cli:jaspr serve` works as an alternative to
the globally-activated `jaspr.bat`, and resolves the workspace from the repo root.

### KEY API DISCOVERY: `events()` has no `onKeyDown`
`jaspr-0.23.5/lib/src/dom/events.dart` exposes only `onClick`, `onInput`,
`onChange`. A named `onKeyDown:` is a **compile error**.

Workaround that works: the `events` param is a `Map<String, EventCallback>`, so
pass a raw map with the helper spread in:
```dart
events: {
  ...events(onClick: () {}),
  'keydown': (event) {
    final key = (event as dynamic).key;
    if (key == 'Escape' || key == 'Esc') setState(() => _open = false);
  },
},
```
This compiles and works. Remember it for any future keyboard handling.

# 2026-10-14 (recurrence) — the stale-server port clash happened AGAIN

Same symptom, second time. `jaspr serve` built fine, then failed to bind 8090
(`errno 10048` EADDRINUSE).

**This time:** PID **25712** (`dartvm.exe`) held 8090 and **16568**
(`dartaotruntime.exe`) held 8181. They had an ESTABLISHED link to each other —
an unmatched parent/child pair from an earlier run. `taskkill /PID 25712 /F`
freed both (the child exited with its parent, so the second taskkill reported
"not found" — that is success, not failure).

So the pattern is confirmed and recurring: **a previous `jaspr serve` outlives
the terminal that started it.** The build succeeds, the new server cannot bind,
and the *old* server keeps serving *old* assets — which is indistinguishable
from "my changes had no effect".

### Two escape hatches
1. **Kill and restart** — `netstat -ano | findstr :8090`, note the LISTENING
   pid, `taskkill /PID <pid> /F`.
2. **Just use another port** — `jaspr serve` has `-p, --port` (confirmed via
   `dart run jaspr_cli:jaspr serve --help`), e.g. `-p 8091`. This is the
   lower-friction option and needs no process hunting.

Also useful from that help output: `--web-port` (default 5467) and
`--proxy-port` (default 5567) exist for running **multiple** projects, and
`--mode refresh|reload` controls the reload strategy.

### Context worth keeping
`fyp_jaspr_web/pubspec.yaml` has a `jaspr:` section setting `port: 8090`,
added earlier because **8080 is permanently occupied on this machine** — so
8080 is *not* available as a fallback. 8091 or 8092 are safe next ports.

Lesson (same as before, now twice-confirmed): when the user says "the UI
didn't change", check for a stale server **before** re-reading any code.

**errno 231 is Windows named-pipe exhaustion** — the same "pipe pool" limit that
has always blocked `dart test` and `flutter analyze` on this machine. Only 5

next attempt inherits the pipe pressure.

# 2026-10-14 (last) — Sidebar status + the mockup's real structure

User asked whether the sidebar had been removed for the new layout. Answer: **no,
it was not removed.** Verified state:

## The mockup has NO left nav sidebar
`sitewise_dashboard.html` uses a **pill-shaped top nav**
(`bg-white rounded-full shadow-soft sticky top-4`, line 73) plus a two-column
grid whose `<aside>` (line 291, `lg:col-span-4 xl:col-span-3`) is the
**"Listing Board"** — a *content* panel on the RIGHT, not navigation.

So the mockup's "sidebar" was ported as `.dash__board`. The Sitewise left nav
rail is the app's own shell and was kept. The mockup's layout therefore sits
**nested inside** Sitewise's shell, rather than replacing it — that nesting is
the structural reason the dashboard doesn't look like a 1:1 copy of the mockup.

## Fixed: `--content-max` was bypassed
`:root` defines `--content-max: 1180px`, used by the public `.container`
(line 239) and line 572 — but `.app-content__inner` hardcoded **1080px**. So
every authenticated page rendered 100px narrower than the public site, and the
token was silently bypassed (audit C-08 pattern). Changed to
`max-width: var(--content-max)`; now used in 3 places. Compiles clean.

Remaining hardcoded `max-width` values are legitimate: `ch`-based text measures
(46ch/60ch) and component caps (420px dialog, 560px, 620px) — not layout
containers.
