## D02 — BDJ Rule Review (CP-03F-03)

The directive asks specifically whether each rule is a contradiction or an undecided planning
assumption. Applying that test honestly, **all four fail as `SOURCE_CONFLICT`**.

| Rule | Trigger | Verdict | Reasoning |
|---|---|---|---|
| `M2V1_PRODUCT_EMPHASIS_UNDECIDED_PRODUCTS` | `M2V1-03=[UNDECIDED]` + `M2V1-06 ∈ {QUALITY, DISTINCTIVE_CONCEPT}` | **NOT A CONTRADICTION** — planning uncertainty | A business may legitimately intend a quality position before fixing the range. Both statements can be true simultaneously. |
| `M2V1_PRODUCT_PREFERENCE_UNDECIDED_PRODUCTS` | `M2V1-03=[UNDECIDED]` + `M2V1-09 ∋ PRODUCT_PREFERENCE` | **RESEARCH CLARIFICATION REQUIREMENT** | The stimulus is undefined, but the entrepreneur may intend to use the research *to decide* the range. Not a logical conflict. |
| `M2V1_SEGMENT_INTEREST_UNDECIDED_GROUPS` | `M2V1-04=[UNDECIDED]` + `M2V1-09 ∋ SEGMENT_INTEREST` | **RESEARCH CLARIFICATION REQUIREMENT** | Same structure: the population is undefined, not contradictory. |
| `M2V1_DELIVERY_WITH_ON_PREMISE_OCCASION` | `M2V1-02=DELIVERY` + `M2V1-07 ∈ {STUDY_WORK, SOCIAL, LEISURE}` | **NOT A CONTRADICTION** | As the directive notes, delivery-only can serve social occasions outside the premises (group orders, office delivery). |

**Recommendation: do not adopt `BDJ-M2V1-0.1-CAND` as a `SOURCE_CONFLICT` ruleset.** All four are
better classified `INFORMATION_GAP`, which the `Finding` contract already permits — but that is a
contract/classification change, not a rename, and it is the Owner's decision.

### Consequence for BDJ-RULE-COVERAGE-01 — the finding must be restated

Combined with the CP-03E result, the accurate position is:

1. The M2V1 instrument **structurally prevents** every cross-item contradiction (derived options,
   `exclusive`, `requires_priority`) — proven by execution, §D04.
2. The four remaining candidates are **not contradictions** on review.
3. Therefore **no defensible deterministic contradiction rule exists for M2V1.**

Because the admission contract requires a model finding to map to a rule the deterministic detector
also fired, and that set is empty, **cloud BDJ cannot contribute findings on M2V1 by design**. That
is a coherent outcome, not a bug — but it means "BDJ coverage" for M2V1 cannot be delivered by
writing more contradiction rules. It requires an Owner decision on whether BDJ should carry an
`INFORMATION_GAP` class instead.

### Owner decision — TAKEN: retire

Adopt / reject `BDJ-M2V1-0.1-CAND` **as `INFORMATION_GAP`** (requires contract change), or retire it
and accept that M2V1 BDJ is contradiction-free.

**Decided 2026-11-17: retire.** Recorded in
`docs/cp00_integration/PROJECT1_D02_RULESET_RETIREMENT_DECISION_20261117.md`. The module was removed
from `bdj.RULE_MODULES` (so no adoption receipt can activate it), the module is marked

### Proposed additive migration — **NOT APPLIED**

Written to `backend/migrations/project1_ai/20261117_02_finding_provenance.sql`, following the
existing ledger migration's conventions exactly (review-candidate header, `migration_target` +
`migration_receipt` guard, `schema_versions` insert, `owner_scope` + `technical_audit_read`
policies, `immutable_history` → `deny_mutation`).

```sql
CREATE TABLE project1_ai.finding_provenance (
  finding_id          uuid PRIMARY KEY,
  owner_user_id       uuid NOT NULL,
  assessment_id       uuid NOT NULL REFERENCES public.m2_assessments(id),
  assessment_revision integer NOT NULL CHECK (assessment_revision >= 0),
  FOREIGN KEY (finding_id) REFERENCES public.m2_bdj_findings(id),
  execution_mode      text NOT NULL CHECK (execution_mode IN ('DETERMINISTIC','CLOUD')),
  run_id              uuid,
  attempt_no          integer CHECK (attempt_no BETWEEN 1 AND 6),
  output_digest       text CHECK (output_digest ~ '^[a-f0-9]{64}$'),
  ruleset_version     text NOT NULL CHECK (length(ruleset_version) BETWEEN 1 AND 32),
  prompt_version      text,
  model_requested     text,
  model_returned      text,
  admission_status    text NOT NULL CHECK (admission_status IN ('ADMITTED','REJECTED','HELD')),
  source_fingerprint  text NOT NULL CHECK (source_fingerprint ~ '^[a-f0-9]{64}$'),
  created_at          timestamptz NOT NULL DEFAULT now(),
  CHECK ((execution_mode = 'CLOUD') = (run_id IS NOT NULL)),
  FOREIGN KEY (run_id, owner_user_id, attempt_no)
    REFERENCES project1_ai.attempts(run_id, owner_user_id, attempt_no)
);
```

Four corrections to the earlier sketch, each forced by the existing schema:

1. **`owner_user_id` added.** The ledger's `owner_scope` policy scopes on
   `owner_user_id = current_setting('project1.actor_id')::uuid`. Without that column the table
   could not carry the same policy, and RLS would have to be invented rather than mirrored.
2. **Composite FK to `attempts`, not `runs`.** `runs` alone cannot say *which* attempt produced the
   output. `MATCH SIMPLE` means a NULL `run_id` skips the check — exactly the deterministic case.
3. **FK to `public.m2_bdj_findings(id)`.** Provenance may not describe a finding that does not
   exist. This also means a cloud result still cannot be written unless the finding is first
   admitted and persisted by the existing service.
4. **`schema_versions` insert**, so re-application fails closed.

Raw prompt, completion and provider payload are still excluded; only identifiers and digests.

## D10 — UI-07: cross-language canonical JSON and snapshot digest (FIXED)

CP-03E recorded UI-07 as *"untested"*. Probing both implementations directly shows it was not merely
untested — **it was wrong**, and the failure was reachable.

The server hashes with Python's
`json.dumps(v, sort_keys=True, ensure_ascii=False, separators=(",",":"), allow_nan=False)`
(`project1.contracts.canonical`/`digest`, `business_context_v1.source_hash`, and the inline snapshot
digest in `m2_service`). The Dart client recomputed it with `jsonEncode`, which is **not**
byte-equivalent for doubles:

| Value | Python | Dart `jsonEncode` | Equal |
|---|---|---|---|
| `1e-6` | `1e-06` | `0.000001` | no |
| `1e-7` | `1e-07` | `1e-7` | no |
| `1e16` | `1e+16` | `10000000000000000.0` | no |
| `1e17` | `1e+17` | `100000000000000000.0` | no |
| `1e20` | `1e+20` | `100000000000000000000.0` | no |
| `1e21` | `1e+21` | `1e+21` | yes |
| `1.5`, `0.1`, `1/3`, `5e-324`, max double | — | — | yes |

Consequence: any confirmation whose snapshot carried a float at or beyond those magnitudes made
`ApiM2Repository.confirm()` throw `Confirmation snapshot fingerprint mismatch` on a **valid** server
response — a client-side rejection of correct data, indistinguishable from tampering.

**Fix.** `_sourceCanonical` was extracted to a public `canonicalSourceJson` and every double is now
routed through a Python-compatible formatter: shortest round-trip digits (as
`toStringAsExponential` already produces), exponential notation when `decpt <= -4 || decpt > 16`,
exponent padded to two digits, and `.0` appended to integral fixed-form values. Non-finite doubles
throw, matching `allow_nan=False`. Non-string object keys throw instead of being silently coerced.

**Proof.** `shared_logic/test/fixtures/m2_canonical_equivalence.json` is generated by the Python
implementation itself — 919 cases: 629 powers of ten spanning `1e-320`…`1e308`, 240 random
bit-pattern doubles, threshold neighbours, ints, strings (quotes, backslash, newline, tab, NUL,
U+2028, CJK, emoji), bools, null, nested containers, and two realistic M2 confirmation snapshots
with their Python digests.

| Assertion | Result |
|---|---|
| Dart canonical bytes equal Python for all 919 cases | **919 / 919** |
| Dart sha256 over canonical bytes equals Python digest | **2 / 2** snapshot cases |
| `jsonEncode` still diverges on the boundary values (regression guard) | holds |
| Signed zero preserved (`0.0` / `-0.0`) | holds |
| Ints stay ints, non-finite rejected, non-string keys refused | holds |

`shared_logic/test/m2_canonical_equivalence_test.dart` — **14 tests, all passing.**

## D16 — M2-WRITE-01: four causes, one write path

Every M2 write failed `503 M2_SOURCE_UNAVAILABLE` because `refresh_m2_workflow` is a
`CONSTRAINT TRIGGER … DEFERRABLE INITIALLY DEFERRED` on 14 tables: it runs at `COMMIT` with the
caller's rights, and the route maps any `SQLAlchemyError` to a fixed 503.

| # | Cause | Repair |
|---|---|---|
| 1 | `EXECUTE` on both trigger functions revoked from `PUBLIC`, granted to nobody | `20261117_04` |
| 2 | No `SELECT` on `m2_workflow_summary` / projection, no policy on the projection | `20261117_04` |
| 3 | Six relations read by the `security_invoker` views ungranted; six with RLS and **zero** policies | `20261117_05` |
| 4 | The CQ bridge replaced `m2_workflow_campaigns`, adding four `cq_*` relations | `20261117_06` |

Cause 3 was the dangerous one. Granting `SELECT` without policies would have turned a loud 503 into
a silent one: `objectives`, `candidates` and provenance would have been recorded as empty in every
projection while the snapshot still claimed completeness. `20261117_05` therefore grants **and**
scopes, following the existing indirect convention (`objective_id IN (SELECT id FROM
m2_confirmed_uncertainties)` → `… m2_confirmation_snapshots` → `m2_assessments.owner_scope`), which
is actor-scoped transitively because RLS applies to the referenced table inside the policy.

Policies are `FOR SELECT` only; no write privilege is added, and each migration asserts in-transaction
that `INSERT`/`UPDATE`/`DELETE` remain absent and that RLS is still on.

Verification with data, not just catalogs: as `p1_m2_runtime` with the actor bound,
`m2_workflow_summary` for `da90aa4a-…` now returns `objectives[0].origin = "ENTREPRENEUR"` from
`m2_research_objective_sources` — the default-deny table. Cross-owner isolation re-checked
(`OWNER→own 1`, `OWNER→other 0`, `E2E→own 1`, `E2E→other 0`).

> `scripts/cp03f_m2_view_closure_audit.py` derives the relation set from `pg_depend` by walking the
> views' `_RETURN` rules. The earlier hand-maintained lists are why causes 3 and 4 survived two
> rounds of grants.

## OD-3 — Open decision: REQUIRED GEO item is unreachable in the UI

**Facts.** `M2V1-01` is `REQUIRED`, `answer_kind=GEO`. `validate_m2_answer` accepts `UNDECIDED`
before consulting the catalogue, and refuses any concrete area with
`422 The approved versioned GEO catalogue is unavailable`. The panel's `_editable` returns false for
every `kind == 'GEO'`, so it renders no value control; `_stateRecordable` is false because the item
is applicable, so it renders no state control either. The item is inert.

**Consequence.** Through the application, a REQUIRED item cannot be answered, `BDJ` refuses with
`409` naming it, and the workflow cannot reach confirmation. Through the API it completes (D12).

**Two resolutions, and they are not equivalent:**

1. Treat the panel as too strict: allow the registered `UNDECIDED` option for `GEO` items, matching
   the validator. Risk: a REQUIRED area question becomes satisfiable without an area.
2. Treat the validator as too permissive: refuse `UNDECIDED` for a REQUIRED `GEO` item until the
   catalogue is `VERIFIED`. Risk: no M2V1 assessment can be completed at all until the catalogue is
   approved.

This checkpoint does **not** choose. Both change what a REQUIRED answer means, which is a product
and scientific decision, and §10 forbids self-adopting rules.
