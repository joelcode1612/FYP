## Final 48-target capture plan (plan version 9)

The 80-target plan is superseded. New sessions capture **exactly 48** targets;
`buildPlanV9` never densifies — a lens too narrow to keep the previous frame
visible records a note and keeps 48.

**Why 48 works when 80 was "needed".** The saved frame is portrait 3072×4096 at
65° vFOV → hFOV 51.08°, so `tan(hH)=0.4774 < tan(hV)=0.6371`. In the active
target's frame `x = tan(Δyaw)/cos(Δpitch)/tan(hH)`, `y = tan(Δpitch)/tan(hV)`.
A 12-target ring is 30° apart in yaw → x = 1.21 (outside) *regardless* of ring
pitch, which is why ring-by-ring capture could never satisfy the visibility rule
and why plan 7 used a 10% safe margin to reach 80. Fix: stagger upper/lower by
15° and walk one tour (`M0→L15→F30→L45→M30→U45→C60→U75→M60→…`), so **every**
step is 15° yaw + 30° pitch → max |x| 0.648, max |y| 0.938. Margins: max yaw step
25.5°, max pitch step 32.5°.

**Measured (Dart and Python agree).** 48 targets, rings 12/12/12/6/6, pitches
0/±30/±60. 47/47 transitions visible, worst 0.9382 at 8→9 (x 0.5608); with the 2°
shutter tolerance worst 0.993 — still inside. Consecutive overlap min 37.3%,
median 42.5% (24×24 footprint sample, `_basis`/`_dot` from plan_v9). Coverage
100.00% single / 100.00% double, 0 uncovered, no isolated
targets, min 6 connections per photograph. Pole inside the ±60° frames at 0.906
of the half-height. Polar pitch tuning: ±58° → 0.901 but only 0.5° of polar
margin; ±62° fails 12 transitions at 1.012; ±60° is the flattest ring that keeps
the zenith.

**48 was already plan 5's count.** A session now stores `planVersion`
(`sphere_capture_session.planVersion`, read by `_readPlanVersion`) and
`planVersionMatchesCount` replaces the count→version derivation;
`buildSitewiseSessionTargets(count, planVersion:)`, the coordinator
(`capturePlanVersion`) and the upload queue all use the *stored* version.
`sitewisePlanVersionForCount(48)` → 9. Backend `_same_capture` still compares only
mode+expected_frames so an in-flight plan-5 job's idempotent retry reuses its row.

**Payload contract.** Device sends snake_case (`target_id/yaw_deg/pitch_deg/ring/
capture_order`); `PlanPayload` parses it and `_plan_geometry` converts to the
camelCase the mirrors read. Verified with a real dump: 0 problems from
`plan_v9.validate_plan_geometry`, `matchesCanonical: true`, `distinctHeadings: 24`,
`ringCounts` 12/12/12/6/6. Both sides now pin this with a test.

**UI.** `capture_plan_guide.dart` → `kSpherePlanV9`; overlap % is measured from
`planV9Audit`, not hardcoded. Progress map and mini-sphere derive ring ovals from
the targets' own pitches (no hardcoded ±40). The ±40° copy left in

## Plan version 10 — interleaved arches (supersedes the plan-9 tour)

The user supplied `sitewise_48_interleaved_capture_plan.json` as the canonical
geometry and asked for interleaved (not ring-by-ring) guidance. Plan 9's tour
went down-first from M0; the supplied plan goes up-first from M0, so the **ids
differ** even though the step set is identical. Plan 10 was allocated rather
than redefining plan 9, and plan 9 stays readable (the codebase's pattern for
5/7/8).

**Traversal.** `M(30k) → U(30k−15,+30) → C(30k,+60) → U(30k+15,+30) →
M(30k+30) → L(30k+15,−30) → F(30k+30,−60) → L(30k+45,−30) → M(30k+60)`, i.e.
each middle target is followed by an arch that climbs or drops and returns.
Rings 12/12/12/6/6 at 0/±30/±60; every step 15° yaw + 30° pitch; no consecutive
pair shares a ring.

**Verified against the supplied file, not just internally.** The mirror
reproduces the JSON's projected values exactly: 1→2 x 0.64755 y −0.906258,
2→3 −0.551075/−0.874843, 3→4 −0.318163/0.937674, 4→5 −0.560795/0.938228.
47/47 visible, worst 0.9382. Measured here: single 100.00%, double 100.00%,
min consecutive projected overlap 37.3% (24×24 sample), circle-model min
neighbour overlap 33.7%, 0 isolated, connected, `notes` empty at the documented
lens. The JSON reports 37.62% with a denser sample — consistent.

**§4 tolerance finding.** The thinnest frame margin is **1.59°**, *inside* the
existing 2.0° alignment cone, so "inside the cone" does not prove the previous
photograph is still in frame. Rather than shrink the cone globally (which would
make the 3.28°-margin steps harder for no benefit), the shutter now also
projects the previous target at the measured orientation
(`_previousTargetInFrame`, using the plan's own camera profile) and the hold ring
only fills when both hold. Applied at the shutter re-check as well, so a drift
between hold-complete and shutter cannot slip through.

**Backend.** `plan_v10.py` reuses plan 9's version-neutral machinery
(`transition_audit`, and the new `compare_geometry` / `summarise_geometry`), so
the two mirrors cannot drift. `_pole_frames(records, plan_version)` replaced the
id-set guess (`{13,38}` / `{19,56}`) that could give a mid-column frame nadir
projection: poles now come from recorded pitch (≥80°), and oblique-only versions
{4,5,6,7,8,9,10} get no pole ids at all. `stitch_equirectangular` gained
`plan_version`. Also fixed `backend_frame_connection._ensureSession`, which
created the backend session with a hardcoded `kAdaptiveSpherePlan` (44 targets) —
now the session's own version, or plan 10 for a new one.

**Registration graph** is already geometric (`alignment/pairs.py` scores by
projected overlap then prefers adjacent rings). Added a test over real plan-10
frames: every frame gets partners, every frame gets a **cross-ring** partner, and
the candidate graph is connected across all 48.
