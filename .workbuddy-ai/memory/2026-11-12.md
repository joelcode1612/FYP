## ARCore channel audit (2026-11-12) - one real defect found + fixed

- Audited every Dart-read key vs every Kotlin-written key in the AR host.
  RESULT: `probeDirections` was the only mismatch. Kotlin returns an outcome
  map `{results: [...]}` (ArCoreSessionController.kt ~line 630); Dart read it
  with `invokeListMethod`, which casts the Map to List -> TypeError on EVERY
  scan. CaptureController.probeTargets caught it and emitted "Could not scan
  the directions: type 'Map...' is not a subtype of 'List<dynamic>?'", so all
  26 targets stayed "no surface" and the target list said "0 with a surface".
  This bug exists in the upstream reference too. Fixed in
  ArCoreHost.probeDirections: invokeMethod<dynamic>, accept map-with-results OR
  bare list, empty map => empty probe list (never a fabricated hit).
- Everything else in the contract matches: start({width,height,planes:true}) ->
  {textureId,planes,anchors,cameraImage,reused}; pose event keys
  (planeCount/planesTracked/walls/floors/ceilings, activeAnchorId,
  trackingContinuityBroken...); imageOrientation {axisX,axisY}; error {message};
  setMesh {id,positions,colors}; setScene {draws:[{meshId,anchorId,
  localRotation,modelMatrix,scale,offsetX/Y/Z,tintRGBA,useTint,opacity,
  requireTracking,useModelTranslation}]}; raycast/createAnchor/refreshAnchor
  use invokeMapMethod and Kotlin returns maps; takeStill {jpeg,imageWidth,
  imageHeight,sourceImageWidth,sourceImageHeight,rotationAppliedDeg,...}.
- `setPlaneDetection` is defined on ArSessionService but NEVER called - not a
  bug: plane detection is enabled by the `planes: true` argument at start
  (Kotlin PlaneFindingMode.HORIZONTAL_AND_VERTICAL). It is unused API surface.
- Calibration does NOT require a plane (only tracking + fresh pose + usable
  forward direction), so a missed wall/ceiling cannot block a target.
- Plane UI chain verified: ArPoseSample(int fields) -> CaptureState
  (capture_controller ~2681) -> CaptureState.planeSummary ("N planes · W walls ·
  F floors · C ceilings") -> _StatusBar icon/colour.
- Tests: test/ar_capture_integration_test.dart now 15 (4 new channel-contract
  tests with a mocked MethodChannel asserting the {results:[...]} shape, the
  bare-list fallback, empty-map-is-miss, and planes:true at start).
  Full suite 88 pass / 2 skip; analyze clean.

## Body-spin capture fix + handover doc (2026-11-12)

- User reported the amber/orange "limited" ring blocking capture when spinning
  the body around while holding the phone. ROOT CAUSE: 0.20 m station-drift gate
  (VioSphereConstants.maxStationDriftM) measures camera->frozen origin; a body
  spin translates the phone 0.3-0.6 m. Fixed with rotation-aware drift, NOT a
  bypass (kStationDriftGateBypassed stays false).
- New rotation_in_place.dart: establishes an arc only after yaw sweep >= 30 deg
  AND stable radius over a 1.4 s window; freezes radius once (median); gate
  drift = deviation from arc; hard 0.75 m raw cap; radial departure / tracking
  break / clearStation => invalidate => strict raw gate. Frozen origin,
  orientation and all 26 world anchors untouched.
- CaptureGeometryConfig gained rotationInPlaceRadiusM=0.75,
  rotationRadialToleranceM=0.10, minRotationYawSweepDeg=30.
- VioSphereEngine.evaluateFrame gained stationDriftReference; FrameGateEvaluation
  gained rawStationDriftM/rawDriftM. CaptureState gained rawStationDriftM and
  rotatingInPlace. UI status line shows "turning in place" + raw drift.

## Android device bring-up over wireless ADB (2026-11-12)

- `adb pair IP:pairingPort` only pairs; it does NOT connect. `adb connect` must use
  the port on the MAIN Wireless debugging screen ("IP address & Port"), which is
  DIFFERENT from the pairing-dialog port. Ports rotate on every toggle/reconnect.
- On this machine PC Wi-Fi = 10.129.141.217/24, phone = 100.88.109.235 (CGNAT,
  different subnet, mDNS does not cross), so `adb mdns services` is always empty
  and the port must be read manually. Ping works (TTL 64); a bounded TCP scan
  30000-45500 found exactly one open port = the live connection port.
- Working sequence that launched the app:
    adb kill-server; adb start-server
    adb connect 100.88.109.235:<connectPort>   # must show "device", not "offline"
    adb reverse tcp:8090 tcp:8090              # device 127.0.0.1:8090 -> PC:8090
    adb install -r fyp_mobile_app/build/app/outputs/flutter-apk/app-debug.apk
    adb shell monkey -p com.example.fyp -c android.intent.category.LAUNCHER 1
- Verified: adb reverse list "host-27 tcp:8090 tcp:8090"; app PID alive; MainActivity
  resumed; screenshot shows SiteWise home; device /proc/net/tcp shows connections to
  :1F9A (8090) in TIME_WAIT => real API traffic through the tunnel.
